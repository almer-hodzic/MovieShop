## Provider and compatibility

- Infrastructure uses `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.3 with EF Core/Relational 10.0.14. The existing JWT dependency is now explicit at its existing resolved version 8.19.2; it was previously supplied transitively by SQL Server libraries. SQL Server client/provider and the no-longer-needed Pkcs override were removed.
- SQL Server `varbinary(max)` profile data maps to PostgreSQL `bytea`.
- Actor/director birth dates and movie release dates map to `date`, retaining .NET DateTime/API DTOs. UTC audit/auth/cart/notification/checkout instants use provider-default `timestamp with time zone`. No global legacy timestamp switch or weakened timezone behavior is enabled.
- Existing decimal precision stays 18,2 and PostgreSQL uses numeric(18,2).
- Identity keys use PostgreSQL generated-by-default identity. Constants/default booleans, foreign keys and indexes are generated by Npgsql, without SQL Server identity annotations or bracketed SQL.
- Account email/username use `citext` with unique indexes, preserving case-insensitive uniqueness at the database boundary. The baseline enables PostgreSQL's citext extension.
- Movie/category/actor/director/review text-search predicates normalize both operands to lowercase, preserving existing case-insensitive searches. API contracts and query parameters remain unchanged.
- No runtime computed columns, raw SQL persistence queries or SQL default-expression translations were needed. SQL Server-specific historical data backfills stay in the archive and are not executed against PostgreSQL.

## Migration separation

The seven original SQL Server migrations and their snapshot remain byte-for-byte intact under `Market.Infrastructure/Migrations`. This deployment branch excludes that directory from compilation. Only the clean PostgreSQL baseline and snapshot under `Market.Infrastructure/PostgreSqlMigrations` are compiled/discovered.

The PostgreSQL baseline includes the current domain model and CheckoutSessions. It starts a fresh demo database; it is not an in-place conversion of any SQL Server data. Tests assert exactly one selected PostgreSQL baseline and no pending model changes. Future EF migrations must use the PostgreSqlMigrations output directory/namespace; check that the SQL Server archive has no diff before committing generated files.

Normal Production startup does not migrate or seed. Initialize once using the **direct, non-pooling** Neon connection as `ConnectionStrings__Main`:

```text
dotnet Market.API.dll --initialize-database
```

For this one-off initialization only, set `PublicDemo__Seed=true` and a newly generated nonpersonal `PublicDemo__Password` of at least 16 characters through secret storage. Remove these values from the normal runtime afterward. Use a migration identity with DDL/extension permissions and a least-privilege runtime identity where practical.

## Connection configuration

Keep `ConnectionStrings__Main` as the main backend entry. It accepts an Npgsql connection string or a PostgreSQL URI. Escaped URI credentials are decoded through Npgsql's connection builder, never string-concatenated into SQL or logged. Neon hosts always use SSL **VerifyFull**. No real hostname, password, database URL, API key or token is committed.

If Main is empty, runtime can use Marketplace `POSTGRES_URL`; initialization can use `POSTGRES_URL_NON_POOLING`. Set Main explicitly if the integration supplies differently named URL variables. Do not point initialization at a transaction pooler; use the direct URL. Runtime may use the pooled Neon URL. App pools are capped at 10 connections per instance, minimum zero, idle lifetime 60 seconds. Local Docker tests use SSL-disabled private-network connections only; that is not the Neon configuration.

Backend Vercel root: `MovieShop.Backend`; framework `container`; region `fra1`; existing `Dockerfile.vercel` with pinned official SDK/runtime images, Release publish, dynamic PORT, non-root UID, Production, stdout logging.

Frontend Vercel root: `MovieShop.Frontend`; framework Angular; output `dist/movieshop-frontend/browser`. Set public build variables `MOVIESHOP_API_URL` and `MOVIESHOP_PAYPAL_SANDBOX_CLIENT_ID`. The prebuild generates ignored production config. Local builds use clearly non-deployable fixtures; do not deploy those artifacts.

## Durable checkout

The HTTP checkout API is unchanged. The internal store is now scoped/async EF persistence. CheckoutSessions uses the PayPal OrderId as the session primary key and stores owner UserId, frozen amount/currency, captured flag, UTC creation and expiry timestamps. It has an expiry index and a restricted user foreign key.

Sessions retain a three-hour lifetime. Expired sessions cannot be read or captured. A new checkout deletes at most 100 expired rows via a relational delete; concurrent instances can safely clean the same rows. No always-on cleanup worker, Redis, in-process checkout cache, or payment redesign is required. Capture marks the persisted flag without extending expiry. Existing owner/admin restrictions and provider safeguards remain in place.
